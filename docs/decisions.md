# Open Decisions

Decisions the build has defaulted conservatively. Base Recruits is owned by the founder and Jonathan Caceres; it is a
separate company from any other venture. Each default is implemented, tested and
changeable with one migration or config edit. Recommended answers are engineering recommendations, not legal advice.

## Founder decisions

| # | Decision | Current default | Trade-off | Recommendation |
| --- | --- | --- | --- | --- |
| F1 | Supabase project for Base Recruits development | **Decided 2026-10-22; created 2026-10-23 by the founder:** project "Base Recruits" (us-east-2) in its own Base Recruits organization (Pro). Migrations deploy from `main` through Supabase's GitHub integration; preview branching off (`docs/deployment.md`) | On the Pro plan every member of an organization can open every project in it, so anyone added for Base Recruits also sees the other projects there | Done. An unused empty project in the same organization (ca-central-1) should be deleted by the founder
| F2 | Who reviews coach verifications, and how fast | **Decided 2026-10-22: Adam Concadoro (founder) reviews coach verifications.** Backup reviewer and turnaround target not yet set | Every verified coach is a manual review; slow reviews stall Pillar C's network value, and a single reviewer is a bottleneck when away | Name a backup and set a 2-business-day target before Stage 4 |
| F3 | Coach verification evidence standard | Official staff-directory page on an https athletics site listing the person in a baseball role; valid 365 days | Stricter evidence slows onboarding; looser evidence lets non-coaches reach minors' profiles | Keep; add "institution email domain matches the program's official domain" as a reviewer checklist item in Stage 2 |
| F4 | Minors' coach-facing sharing needs a linked guardian's approval | **Decided 2026-10-21 by the founder: on** for discovery, academic summary, metrics, contact info, messaging and documents | Strong protection for 13–17-year-olds; adds friction that may slow early athlete discoverability | Keep on for launch; revisit with counsel and real funnel data (`consent_scope_rules.requires_guardian_approval_for_minor`) |
| F5 | What a linked parent/guardian sees by default | Only the basic athlete record; everything else needs the athlete's explicit grant | Respects athlete control; parents of minors may expect more | Keep explicit grants; at link approval, ask the athlete which items to share (no pre-checked boxes) |
| F6 | Can a minor end a parent/guardian link alone | Yes — either party can end a platform link | Platform access is consent-based, but parents of minors may object | Keep, pending counsel (L3) |
| F7 | Support and appeals channel, and the email address Base Recruits sends from | Not decided (founder unsure which address to use, 2026-10-22); UI copy says a support contact will be published before launch; `/support` explains the correction route meanwhile | Coaches need an appeal path; families need privacy-request handling; sign-up codes need a trusted sender | Use addresses on a Base Recruits domain (for example support@ and no-reply@), not a personal or other venture's address; decide before Stage 4 |
| F8 | Paid plan prices | $14.99 / $29.99 / $39.99 proposed, marked as hypotheses, not purchasable | Stage 6 decision | Decide after Stage 5 with usage data |
| F9 | How strongly to verify that a "parent" is a parent | Self-attested adult age and relationship, plus the athlete's approval after seeing the account's name and email | Light verification keeps family onboarding easy; a determined teen with a second account and false answers could still pose as a parent | Keep for launch with audit monitoring; decide on stronger verification before coach messaging with minors (Stage 4) |
| F10 | When to let people change their account email | Off: the database refuses email-change requests | A change confirmed by a link or code sent to someone else's address could hand them that address (for a coach, a path toward a fake verification) | Keep off for launch. When added: confirm by code typed while signed in, and send coaches back through verification |
| F11 | Who approves registry imports | Any administrator can stage, review and publish; today that is the founder (Adam Concadoro). Every publish records who did it, with an optional note, and can be rolled back by restaging an earlier import | A single approver is simple but a bottleneck; a mistaken publish is visible on public pages until rolled back | Keep the founder as approver for launch. Before data partners or staff publish, require a second reviewer for any import that changes or removes more than 50 programs |
| F12 | Athletics association directories (NCAA, NAIA, NJCAA) | **Not used.** Division comes from the school's athletics classification in the federal EADA report; an administrator can correct it citing the association directory or the team's own site | Federal data covers every program in one public file, but its classification is institution-level: 37 programs are reported as "Other", and NCCAA/USCAA members may play baseball under another association | Work through the "Other" queue by hand before launch (admin → Schools and programs). Check each association's terms (L6) before automating any directory |
| F13 | How often the registry is refreshed | Manually: push a `data/*` branch (or run the data-refresh workflow on one), review the snapshot pull request, merge, then stage and publish in the app | EADA publishes once a year (autumn); College Scorecard updates a few times a year. Manual keeps a person in the loop | Refresh each autumn when EADA releases, and when Scorecard announces a data update. A scheduled workflow that only opens the pull request can come later |
| F14 | When search engines may index the site | **Off.** Every page sends `noindex` and `robots.txt` disallows crawling unless `NEXT_PUBLIC_APP_ENV=production` and `ALLOW_INDEXING=true` | Indexing a pre-launch site with draft legal pages and an unconfirmed support route invites traffic the product can't yet serve; waiting delays search visibility | Turn on after legal review (L8), a support address (F7) and the custom domain |
| F15 | Fit labels in the score comparison (Strong / Competitive / Reach or similar) | **None shipped.** Results are grouped only by where scores sit against past-class ranges, with reasons; rules in `src/lib/matching/rules.ts` (`RULES_VERSION`) | Labels are what families expect from competitors, but without published thresholds and outcome data they read as admission predictions | Keep none until the founder approves a written rulebook with explicit thresholds; never derive thresholds with a language model |
| F16 | Registry data corrections from the October 2026 research (37 "Other" programs, Johns Hopkins testing policy) | **Decided 2026-10-23 by the founder:** applied the 12 strongest division corrections, the Johns Hopkins fall 2027 first-year testing policy (required), the LAI label for 8 Puerto Rico programs, and Southwest Virginia discontinued. After a re-check, five more (Snead State, Triton, Southeastern, Marshalltown, Rockland) were applied the same day; Mineral Area, Paradise Valley and Massasoit are held (`docs/remediation/proposed-data-corrections.md`) | Each correction changes public pages; weaker evidence risks a wrong division | Apply the three held rows once a 2026-27 official page names their division |
